# macOS Sequoia base image (2026-10-29)

## Quiet base

`/var/lib/runner-appliances/base/macos-sequoia-15.7.7-runner-quiet-20261029.qcow2`:
the hosted tool cache base of 2026-10-27 (`BASE-20261027.md`) with the
launchd jobs disabled that kept every guest busy while it ran no job. It is
a standalone qcow2 with no backing file, 86.1 GiB on disk, 256 GiB virtual,
`qemu-img check` clean. Toolchains, tool cache, templates, NVRAM seed, SSH
host key and listener state are unchanged, and the base holds no
registration.

### Why

Both pool guests, idle, each cost the appliance host six to eight cores and
the host sat at a load of 13 on 16 vCPU. Inside each guest three daemons ran
flat out and had done so since boot (18 to 33 hours of CPU in 36 hours of
uptime):

| Process | CPU | What it was doing |
| --- | --- | --- |
| `apsd` | 85-93 % | looping on a CFPrefs write its sandbox refuses ("setting these preferences requires user-preference-write or file-write-data sandbox access"), 73 times per 90 s |
| `PerfPowerServices` | 82-98 % | polling SMC metrics (`PLSMCMetricsAgent`) that a QEMU guest cannot provide |
| `opendirectoryd` | 93-135 % | account-policy evaluations driven by `apsd`; it fell to 17 % the moment `apsd` was gone |
| `cloudd` | 15-20 % | iCloud sync for an account that does not exist |

The effect on jobs: the same pytest suite of one commit took 8.9 s on the
Linux runner, 16.5 s on Windows and 115 s on macOS, and a 0.25 s wall-clock
assertion in it failed on macOS alone (deepseek-bridge run 20, 2026-10-29).
A job on one guest competed with its own guest's daemons and with the idle
neighbour's.

Disabling the jobs in the two live guests dropped their host-side QEMU CPU
from 501 % and 578 % to 173 % and 152 %, and the appliance load from 13 to 3.5.

### What is disabled

System domain (`launchctl disable system/<label>`):
`com.apple.apsd`, `com.apple.PerfPowerServices`,
`com.apple.PerfPowerServicesExtended`, `com.apple.cloudd`,
`com.apple.cloudd.system`, `com.apple.cloudd.system.cache`.

User domain of `user` (uid 501, `launchctl disable gui/501/<label>`):
`com.apple.cloudd`, `com.apple.itunescloudd`.

Nothing else changed. `softwareupdated` still runs at boot and is worth a
look next: it took a full core for the first minutes of every boot.

### How it was made

The same maintenance-guest procedure as `BASE-20261027.md`: an overlay on
the 2026-10-27 base started exactly as the pool starts a runner guest (the
appliance image's own command behind `/usr/local/bin/nomercy-appliance-start`,
the same mounts, balloon and QMP socket, `-p 127.0.0.1:51999:10022`, 8 vCPU /
8 GiB), reached over SSH with the guest credential the agent holds. The jobs
were disabled and booted out, the guest shut down with `/sbin/shutdown -h now`,
booted a second time to confirm a clean start (the boot storm settles within
five minutes; none of the disabled daemons came back), shut down again, and
the overlay flattened with `qemu-img convert -O qcow2` once QEMU had exited.
The `.native.json` was written from the previous base's attestation with the
new `base_disk` and `base_identity`, and checked by instantiating
`NativeProvisioner` against it.

Switching bases is all-or-nothing: both macOS runners are retired, then
`appliance_pool.base_disk` in the appliance host's `agent.json` names this
file, `runner-agent` is restarted, and one runner per macOS fleet is created
again. A `recreate` is not enough: it keeps the runner's overlay, and that
overlay is backed by the old base.
