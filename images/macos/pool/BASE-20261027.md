# macOS Sequoia base image (2026-10-27)

## PHP and Node base

The pool's base disk is now
`/var/lib/runner-appliances/base/macos-sequoia-15.7.7-runner-phpnode-20261027.qcow2`:
the toolchains base of 2026-10-26 (`BASE-20261026.md`) with PHP and Node
moved to the versions every other runner platform runs. It is a standalone
qcow2 with no backing file. The NVRAM seed, the SSH host key and the
listener state are unchanged, and the base holds no registration.

| Tool | Before | Now | Where |
| --- | --- | --- | --- |
| PHP | 8.5.6 (Homebrew) | 8.5.12 | `/usr/local/php-8.5.12`, linked into `/usr/local/bin` and `/usr/local/sbin` |
| Node | 26.0.0 (Homebrew) | 26.12.1 | official `darwin-x64` tarball unpacked into `/usr/local` |
| npm | 11.x | 11.20.0 | bundled with Node |

Homebrew's `php` and `node` formulae are uninstalled, so one PHP and one
Node remain. PHP keeps reading `/usr/local/etc/php/8.5/php.ini` and its
`conf.d`, and loads the same 67 extensions as the 8.5.6 build.

## Why not Homebrew

Homebrew no longer builds bottles for Intel macOS. `brew update` on this
guest installs a Homebrew that refuses `brew upgrade` on x86_64 ("not a
Tier 1 configuration"), and the `php` formula only ships ARM and Linux
bottles. **Do not run `brew update` in a base guest.** Install with
`HOMEBREW_NO_AUTO_UPDATE=1` when a formula is genuinely needed.

## How PHP was built

From `php-8.5.12.tar.xz` (php.net SHA-256
`08bc2eba2a588654ade1357174aa646b761556c862dda0678345ee29ed481209`) with the
`Configure Command` of the Homebrew 8.5.6 build, except:

- `--prefix` and `--with-pear` point under `/usr/local/php-8.5.12`;
- `--with-apxs2` is dropped: no Apache module on a runner;
- the options that pointed at the Command Line Tools SDK 14
  (`--with-bz2`, `--with-iconv`, `--with-mhash`, `--with-ndbm`) point at
  `xcrun --show-sdk-path`, the SDK of the compiler in use. Mixing SDK 14 C
  headers with Xcode 16.4's libc++ headers broke every C++ file in `intl`;
- `LDFLAGS` starts with `-L/usr/local/opt/{openldap,tidy-html5,net-snmp}/lib`.
  The macOS SDK ships old `libldap`, `libtidy` and `libnetsnmp`; without
  this the link picks Apple's copies and fails on missing symbols.

## Node and corepack

Node 25 and later no longer bundle corepack. The old Homebrew Node 26.0.0
had none either. Installing it from npm would overwrite the Homebrew
`yarn` and `pnpm` already on the PATH, so it is left out on macOS.

## How it was made

Same maintenance-guest procedure as `BASE-20261026.md`: an overlay on the
previous base started exactly as the pool starts a runner guest, changes
made as `user`, caches removed, `/sbin/shutdown -h now`, `qemu-img convert`
once QEMU exited, a `.native.json` written with the agent's
`base_identity` and checked by instantiating `NativeProvisioner`, then
stop, retire, switch `appliance_pool.base_disk`, restart `runner-agent`
and create one runner per macOS fleet.

## Next base: the hosted tool cache (pending)

Every macOS job that ran `actions/setup-python` found an empty tool cache,
downloaded Python and ran the python.org installer (`sudo installer -pkg`,
208 s for 3.12). Forgejo failed the task during that install
(FiLL/deepseek-bridge run 989, job 1666, 2026-10-27).

From 2026-10-27 every pool runner's `RUNNER_TOOL_CACHE` and
`AGENT_TOOLSDIRECTORY` name **`/Users/runner/hostedtoolcache`**
(`macos_pool.HOSTED_TOOLCACHE`): the same path for both variables, the one
GitHub's hosted macOS images use. A per-runner path does not work. The
python-versions packages for versions python.org has no installer for
(3.10.22 here, every 3.9 and 3.8) are compiled with
`--prefix=/Users/runner/hostedtoolcache/Python/<version>/x64` and load
`libpython` from that absolute path. Under any other tool cache they abort in
dyld:

```
dyld: Library not loaded: /Users/runner/hostedtoolcache/Python/3.10.22/x64/lib/libpython3.10.dylib
```

The Forgejo launcher writes both variables into `runner.envs` of
`config.yaml` from its launchd environment, together with `RUNNER_NAME` from
`.runner` (Forgejo host mode left it empty).

**The next base must carry the filled tool cache.** Run
`install-runner-toolcache.sh` as `user` in the maintenance guest, after
`install-runner-toolchains.sh`. It installs exactly as setup-python and
setup-node do:

| Tool | Versions | Where |
| --- | --- | --- |
| Python | 3.10.22, 3.11.9, 3.12.10, 3.13.17, 3.14.10 | `/Users/runner/hostedtoolcache/Python/<v>/x64` + `x64.complete`. 3.11+ link into `/Library/Frameworks/Python.framework/Versions/<m.n>`, installed by the package's own `setup.sh` |
| Node | 20.20.2, 22.23.4, 24.22.1, 26.12.1 | `/Users/runner/hostedtoolcache/node/<v>/x64` + `x64.complete`, from the official darwin-x64 tarballs (SHASUMS256 checked) |

These are the newest patch releases python-versions publishes a darwin-x64
package for. The python.org installers also relink `/usr/local/bin/python3*`
to their frameworks. `python3` on the PATH becomes python.org's 3.14.10
instead of Homebrew's 3.14.5. They add no bare `pip` or `python`, which the
health check requires, so the script links both to `pip3` and `python3`.
pnpm 11.5.1 and yarn stay in `/usr/local/bin`.

Until that base exists, the two live guests had the same script run in
place. `/Users/runner/hostedtoolcache` is on the guest's overlay disk, which a
recreate keeps (`remove(keep_data=True)`). A runner *created* on the current
base starts empty and needs the script again.

A build of this base was started on 2026-10-27 in a maintenance guest
(`rnr-maint-toolcache-20261027c`, `/var/lib/runner-appliances/maint-20261027c`,
an overlay on the phpnode base, SSH on 127.0.0.1:51999). It is **paused**
(`docker pause`) with Python 3.10.22 and 3.11.9 installed. Under the 3-CPU cap
it needed to stay clear of the runner guests, the python.org 3.12 framework
`postinstall` (it byte-compiles the standard library) twice exceeded
PackageKit's hard 600 s script limit, and the installer failed: "Task has
exceeded its 600 seconds of runtime" in `/var/log/install.log`. A
maintenance guest running next to two busy runner guests also starved them
into failed recreates once. So finish it only in a window with the runners
offline and the guest at full CPU: `docker update --cpus 8`, `docker
unpause`, run the script again (it skips finished versions), then
`maint5-stage3.sh` (clean shutdown, `qemu-img convert` to
`macos-sequoia-15.7.7-runner-toolcache-20261027.qcow2`), `maint5-stage4.py`
(`.native.json`), and with both runners retired `maint5-stage5.py` (switch
`appliance_pool.base_disk`, restart `runner-agent`), then create one runner per
macOS fleet. The stage scripts are copies of the 2026-10-27 phpnode stages
with the new paths, in `/home/runner/maint5-*` on the appliance host beside
`install-runner-toolcache.sh`.
