# macOS Sequoia base image (2026-10-27)

## PHP and Node base

Superseded the same day by the hosted tool cache base below. This base was
`/var/lib/runner-appliances/base/macos-sequoia-15.7.7-runner-phpnode-20261027.qcow2`:
the toolchains base of 2026-10-26 (`BASE-20261026.md`) with PHP and Node
moved to the versions every other runner platform runs. It is a standalone
qcow2 with no backing file. The NVRAM seed, the SSH host key and the
listener state are unchanged, and the base holds no registration.

| Tool | Before | Now | Where |
| --- | --- | --- | --- |
| PHP | 8.5.6 (Homebrew) | 8.5.12 | `/usr/local/php-8.5.12`, linked into `/usr/local/bin` and `/usr/local/sbin` |
| Node | 26.0.0 (Homebrew) | 26.12.1 | official `darwin-x64` tarball unpacked into `/usr/local` |
| npm | 11.x | 11.20.0 | bundled with Node |

Homebrew's `php` and `node` formulae are uninstalled, so one PHP and one
Node remain. PHP keeps reading `/usr/local/etc/php/8.5/php.ini` and its
`conf.d`, and loads the same 67 extensions as the 8.5.6 build.

## Why not Homebrew

Homebrew no longer builds bottles for Intel macOS. `brew update` on this
guest installs a Homebrew that refuses `brew upgrade` on x86_64 ("not a
Tier 1 configuration"), and the `php` formula only ships ARM and Linux
bottles. **Do not run `brew update` in a base guest.** Install with
`HOMEBREW_NO_AUTO_UPDATE=1` when a formula is genuinely needed.

## How PHP was built

From `php-8.5.12.tar.xz` (php.net SHA-256
`08bc2eba2a588654ade1357174aa646b761556c862dda0678345ee29ed481209`) with the
`Configure Command` of the Homebrew 8.5.6 build, except:

- `--prefix` and `--with-pear` point under `/usr/local/php-8.5.12`;
- `--with-apxs2` is dropped: no Apache module on a runner;
- the options that pointed at the Command Line Tools SDK 14
  (`--with-bz2`, `--with-iconv`, `--with-mhash`, `--with-ndbm`) point at
  `xcrun --show-sdk-path`, the SDK of the compiler in use. Mixing SDK 14 C
  headers with Xcode 16.4's libc++ headers broke every C++ file in `intl`;
- `LDFLAGS` starts with `-L/usr/local/opt/{openldap,tidy-html5,net-snmp}/lib`.
  The macOS SDK ships old `libldap`, `libtidy` and `libnetsnmp`; without
  this the link picks Apple's copies and fails on missing symbols.

## Node and corepack

Node 25 and later no longer bundle corepack. The old Homebrew Node 26.0.0
had none either. Installing it from npm would overwrite the Homebrew
`yarn` and `pnpm` already on the PATH, so it is left out on macOS.

## How it was made

Same maintenance-guest procedure as `BASE-20261026.md`: an overlay on the
previous base started exactly as the pool starts a runner guest, changes
made as `user`, caches removed, `/sbin/shutdown -h now`, `qemu-img convert`
once QEMU exited, a `.native.json` written with the agent's
`base_identity` and checked by instantiating `NativeProvisioner`, then
stop, retire, switch `appliance_pool.base_disk`, restart `runner-agent`
and create one runner per macOS fleet.

## Hosted tool cache base (the pool's base since 2026-10-27)

The pool's base disk is now
`/var/lib/runner-appliances/base/macos-sequoia-15.7.7-runner-toolcache-20261027.qcow2`.
It is the PHP and Node base above with a filled hosted tool cache. It is a
standalone qcow2 with no backing file: 86.1 GiB on disk, 256 GiB virtual,
and `qemu-img check` is clean.
SHA-256: `d945799207d607771cac6cd25a73d82bfee870cbf7306cb73a328d4f65ae9083`.
Its `.native.json` was written with the agent's `base_identity` and
checked by instantiating `NativeProvisioner`. The NVRAM seed, the SSH host
key and the listener state are unchanged, and the base holds no
registration.

### Why

Every macOS job that ran `actions/setup-python` found an empty tool cache,
downloaded Python and ran the python.org installer (`sudo installer -pkg`,
208 s for 3.12) (FiLL/deepseek-bridge run 989, job 1666, 2026-10-27). That
Forgejo task was finally failed by the server, not the runner. The forge's
`ENDLESS_TASK_TIMEOUT` was set to the largest Go duration. The
stop-endless-tasks cron then computed a negative start bound and stopped
every running task every 30 minutes. It is 720h since 2026-10-27.

### The tool cache path

Every pool runner's `RUNNER_TOOL_CACHE` and `AGENT_TOOLSDIRECTORY` name
**`/Users/runner/hostedtoolcache`** (`macos_pool.HOSTED_TOOLCACHE`). Both
variables use the same path, the one GitHub's hosted macOS images use. A
per-runner path does not work. The python-versions packages for versions
python.org has no installer for (3.10.22 here, every 3.9 and 3.8) are
compiled with `--prefix=/Users/runner/hostedtoolcache/Python/<version>/x64`
and load `libpython` from that absolute path. Under any other tool cache
they abort in dyld:

```
dyld: Library not loaded: /Users/runner/hostedtoolcache/Python/3.10.22/x64/lib/libpython3.10.dylib
```

A pool guest holds one runner, so the path is that runner's alone. The
Forgejo launcher writes both variables into `runner.envs` of `config.yaml`
from its launchd environment, together with `RUNNER_NAME` from `.runner`
(Forgejo host mode left it empty).

### What the base carries beyond the PHP and Node base

`install-runner-toolcache.sh`, run as `user`, installs exactly as
setup-python and setup-node do:

| Tool | Versions | Where |
| --- | --- | --- |
| Python | 3.10.22, 3.11.9, 3.12.10, 3.13.17, 3.14.10 | `/Users/runner/hostedtoolcache/Python/<v>/x64` + `x64.complete`, each by the package's own `setup.sh`. 3.11+ link into `/Library/Frameworks/Python.framework/Versions/<m.n>`; 3.10.22 is a prebuilt tree in place |
| Node | 20.20.2, 22.23.4, 24.22.1, 26.12.1 | `/Users/runner/hostedtoolcache/node/<v>/x64` + `x64.complete`, from the official darwin-x64 tarballs (SHASUMS256 checked) |
| pip, python | links in `/usr/local/bin` to `pip3` / `python3` | the health check requires both |

These are the newest patch releases python-versions publishes a darwin-x64
package for. The python.org installers relink `/usr/local/bin/python3*` and
`pip3*` to their frameworks. `python3` on the PATH is python.org's 3.14.10,
not Homebrew's 3.14.5. pnpm 11.5.1, yarn, PHP 8.5.12 and Node 26.12.1 are
unchanged.

The base was checked in the maintenance guest before freezing. All nine
versions have their directory and `x64.complete`, each runs, and Python
3.12 imports `ssl` (OpenSSL 3.0.16) and `tkinter` (Tk 8.6). Every tool the
health check lists resolves on the PATH.

### How it was made

The same maintenance-guest procedure as `BASE-20261026.md` was used: an
overlay on the phpnode base, started exactly as the pool starts a runner
guest; the script run as `user`; caches, history and installer leftovers
removed; `/sbin/shutdown -h now`; `qemu-img convert` once QEMU exited; the
`.native.json`; then stop, retire, switch `appliance_pool.base_disk`, restart
`runner-agent`, and create one runner per macOS fleet.

Two things to know for the next base:

- **Give the maintenance guest the host to itself.** The python.org
  framework `postinstall` byte-compiles the standard library. Next to two
  busy runner guests, with the maintenance guest capped at 3 CPUs, it twice
  exceeded PackageKit's hard 600 s script limit ("Task has exceeded its 600
  seconds of runtime" in `/var/log/install.log`). A maintenance guest
  running next to the runners also starved them into failed recreates.
  Stop the runners first.
- **The first template copy in a new guest is slow.** It reads every file of
  the 440 MB GitHub template from the cold base disk while the fresh guest
  indexes and updates. It ran past the old 300 s copy timeout on an idle
  host and failed `create_unit`. `GuestFs.copytree` now waits 1200 s.
